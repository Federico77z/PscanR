# PscanR developer notes

These notes are for people who maintain or extend PscanR. They describe how
the code is organised, how data move through the package, the conventions the
code follows, how a change is checked, and how it reaches Bioconductor. User
documentation is in the vignettes and the manual pages. The method is
described in Zambelli, Pesole and Pavesi (2009),
<https://doi.org/10.1093/nar/gkp464>.

This file is listed in `.Rbuildignore`: it is part of the repository, not of
the package tarball.

## Repository layout

### `R/`

| File | Contents |
|---|---|
| `AllClasses.R` | The `PSMatrix` and `PSMatrixList` classes and their constructors. |
| `AllGenerics.R` | All S4 generics: exported accessors and internal `.ps_*` generics. |
| `methods-PSMatrix.R` | Accessors, setters, validity and `show` methods; the scanning kernels; the z-test. |
| `Argument_checks.R` | Argument checks shared by the exported functions. |
| `Promoter_selection.R` | One promoter per gene: `ps_select_promoters()`, `ps_load_select_transcripts()`, `ps_selection_summary()`. |
| `Transcript_schemes.R` | Recognising and normalising transcript identifiers (RefSeq, SGD, TAIR, generic). |
| `Build_Background.R` | Building, saving, reading and retrieving backgrounds. |
| `Scan_and_post_processing.R` | `pscan()`, `pscan_filtered()`, `pscan_full_bg()`, result tables and plots. |
| `Helper_functions.R` | Sequence cleaning, the background catalog, ExperimentHub and Zenodo retrieval, SHA-256 checks, shared warnings. |
| `PscanR.R` | Package documentation and the package-wide `@importFrom` directives. |

There is no `Collate` field. Files are sourced in alphabetical order, so
`AllClasses.R` and `AllGenerics.R` come before every file that defines
methods; all methods are in `methods-PSMatrix.R`.

### Other directories

- `tests/testthat/`: test files grouped by area (argument checks, background
  construction, catalog, ExperimentHub and Zenodo retrieval, full-background
  legend, promoter selection, scanning and results), plus
  `test-Manual_contract.R` (behaviour promised by the manual pages: class
  validity, accessor names, coordinates) and `test-Parallel_defaults.R`
  (the serial default gives the same result as an explicit serial backend).
  The tests run offline: downloads are replaced with mocked bindings.
- `vignettes/`: a quick overview, concepts and input, custom backgrounds, and
  two case studies (mouse retina, Arabidopsis BPC). Precomputed inputs for the
  case studies are in `inst/extdata/vignettes/`.
- `inst/extdata/`: small data used by examples, tests and vignettes (example
  promoters, motif collections, a JASPAR 2020 background) and the background
  catalog `PscanR_background_catalog_v2.tsv`.
- `inst/scripts/`: scripts that regenerate the example data.
  `fixture-provenance.md` records where each file comes from and how far it
  can be reproduced.
- `inst/DATA_SOURCES.md` (external data and their terms), `inst/PROVENANCE.md`
  (authorship and AI assistance), `inst/CITATION`.
- `man/`: generated by roxygen2 from the comments in `R/`. Never edit it by
  hand. The current pages were generated with roxygen2 8.0.0; an older
  version can produce unrelated differences.
- `.github/workflows/`: continuous integration (see below).
- `.lintr`: the lint configuration.

## Classes

`PSMatrix` extends `TFBSTools::PFMatrix`. Besides the frequency matrix it
holds:

- background statistics: `ps_bg_avg`, `ps_bg_std_dev`, `ps_bg_size`;
- foreground results: `ps_fg_avg`, `ps_fg_size`, `ps_zscore`, `ps_pvalue`;
- the best hit in each foreground promoter: `ps_hits_score`, `ps_hits_pos`,
  `ps_hits_strand`, `ps_hits_oligo`, named by `ps_seq_names`;
- for a full background, the same four vectors for every background promoter
  (`ps_hits_*_bg`), named by `ps_bg_seq_names`;
- `.PS_PSEUDOCOUNT` and `.PS_ALPHABET`, used to turn frequencies into scores.

`PSMatrixList` extends `TFBSTools::PFMatrixList` and adds
`transcriptIDLegend`, which maps each transcript of a full background to the
promoter scanned for it: transcripts with identical promoter sequences share
one scanned promoter.

Each slot has an exported accessor generic in `AllGenerics.R` and a method in
`methods-PSMatrix.R`; most accessors take `withDimnames`. Users can change
only the three background statistics, through the replacement methods
`ps_bg_avg<-`, `ps_bg_std_dev<-` and `ps_bg_size<-`, which validate the
object. Every other slot is written only in `methods-PSMatrix.R`, by the
internal `.ps_set_*()` helpers and the scanning code.

## Data flow

### 1. Promoter selection

`ps_select_promoters()` maps genes to transcripts, through an annotation
table or an organism annotation package, and keeps one promoter per gene.

- `mode = "select"` (human, RefSeq identifiers) prefers MANE Select, then
  RefSeq Select, then the scheme's own ranking. The Select tables come from
  the UCSC hg38 tracks through `ps_load_select_transcripts()`, which caches
  them under `tools::R_user_dir("PscanR", "cache")`.
- `mode = "representative"` uses only the scheme's own ranking.
- `mode = "all_transcripts"` keeps every mapped transcript.

Identifiers are interpreted by scheme (`Transcript_schemes.R`, through which
all identifier normalisation goes): a RefSeq version such as `.6` is removed
before matching, a TAIR suffix is kept because it denotes a splice variant.

### 2. Backgrounds

A background holds, for each motif, the mean and standard deviation of the
best-hit scores over a reference set of promoters, normally those of all the
genes of an organism.

- `ps_build_bg()` scans a promoter set. With `fullBG = TRUE` it also keeps the
  per-promoter hits and the transcript legend, which `pscan_full_bg()` needs.
- `ps_write_bg_to_file()` and `ps_retrieve_bg_from_file()` save and read the
  text format, which holds the statistics only. A full background is kept
  with `saveRDS()`.
- `ps_get_bg_table()` and `ps_build_bg_from_table()` do the same with a
  `data.frame`.
- `ps_retrieve_bg()` and `ps_available_bg()` use the precomputed backgrounds.

`ps_retrieve_bg()` works as follows.

1. The bundled catalog (`inst/extdata/PscanR_background_catalog_v2.tsv`, or
   the file named by the option `PscanR.background.catalog`) is filtered by
   JASPAR release, organism, promoter window, assembly (optional) and
   background version (the latest by default).
2. The background file is fetched from ExperimentHub, where the
   PscanRBackgrounds package registers each file under the title
   `PscanR_bg_v<version>_<file stem>`.
3. If that fails, a warning is raised and the file is downloaded from its
   Zenodo record (`.ps_zenodo_file_records` in `Helper_functions.R`); with
   `source = "zenodo"` this is the first step. Downloads go into a
   BiocFileCache under `tools::R_user_dir("PscanR", "cache")` (option
   `PscanR.background.cache`). If the download fails, the file is extracted
   from the archive record `.ps_zenodo_record_id`.
4. Whatever the source, the file must match the catalog's SHA-256 checksum.
   A cached file that does not match is removed.
5. The JASPAR CORE collection for the organism's taxonomic group is loaded
   (`.ps_load_jaspar_collection()`). Its matrix IDs must be the same as those
   in the file; `ps_retrieve_bg_from_file()` then combines matrices and
   statistics into a `PSMatrixList`.

### 3. Scanning

`pscan(x, pfms)`:

1. checks its arguments and warns about motifs without background
   statistics;
2. removes duplicated promoters (`unique()`), then keeps the promoters of the
   most common length and removes those with more than 50% `N`
   (`.clean_sequence()`, which reports both removals in warnings);
3. stops if the promoters kept are shorter than any motif
   (`.ps_check_motif_widths()`);
4. warns if the foreground is large compared with the background
   (`.ps_warn_foreground_fraction()`, threshold option
   `PscanR.foreground.max_fraction`);
5. encodes the promoters once (`.ps_encode_seqs()`) and scans each motif with
   `ps_scan()` through `BiocParallel::bplapply()` (serial by default).

For each promoter `ps_scan()` keeps the best hit on either strand. The
batched kernel (`.ps_scan_batched()`) uses `Biostrings::PWMscoreStartingAt()`
when the promoters contain no ambiguous bases, and a block-wise matrix
implementation otherwise. Promoters of different lengths cannot be encoded
as one matrix; they are scanned one at a time by `.ps_scan_s()`, which only
happens when `ps_scan()` is called directly, and with a warning.

Raw scores are normalised to [0, 1] between the motif's minimum and maximum
score (`.ps_norm_score()`). For the foreground, `.ps_store_fg_hits()` then
computes a one-sample upper-tail z-test of the mean best-hit score against the
background mean, with standard error `ps_bg_std_dev / sqrt(n)`, and the
p-value with `pnorm(lower.tail = FALSE)`. For a background scan,
`.ps_store_bg_hits()` stores the mean and standard deviation instead.

Variants:

- `pscan_filtered()` cleans the promoters as `pscan()` does, keeps those
  whose best score for the motif `Jmatrix` is at least (for negative `n`, at
  most) `ps_bg_avg + n * ps_bg_std_dev`, and scans the promoters kept with
  every motif of `background`.
- `pscan_full_bg()` does not scan. It looks the transcripts up in a full
  background through `transcriptIDLegend` and uses the stored hits.

### 4. Results and plots

`ps_results_table()` collects the statistics of all motifs, adds the
Benjamini-Hochberg FDR and sorts by p-value, then z-score. `ps_z_table()`
returns the standardised best-hit score of each promoter for each motif, and
`ps_zscore_heatmap()` draws it. `ps_hitpos_map()` and `ps_density_plot()`
show where hits fall along the promoters, `ps_hit_score_plot()` plots hit
position against score, `ps_motif_barplot()` shows the most enriched motifs,
and `ps_motif_class()` returns the structural class of each motif's
transcription factor.

## Conventions

- **Style.** Four-space indentation and lines of at most 80 characters,
  enforced by `.lintr` (lintr defaults, `indentation_linter(indent = 4L,
  hanging_indent_style = "never")`, several object-name styles allowed for
  Bioconductor names; `inst/scripts` excluded). The CI lint job fails on any
  lint, so run `lintr::lint_package()` before pushing.
- **Function length.** Functions stay within about 50 lines, the Bioconductor
  guideline. Longer logic is split into named helpers, some of them used
  once.
- **Names.** Exported functions start with `ps_` or `pscan`. Internal
  functions and generics start with `.ps_` and are documented with `@noRd`.
  A few older internal helpers (`.clean_sequence()`,
  `.mapping_unique_names()`) keep their names.
- **Argument checks.** Each exported function checks its arguments first,
  with the helpers in `Argument_checks.R` (`.ps_assert_class()`,
  `.ps_assert_character()`, `.ps_assert_string()`, `.ps_assert_flag()`,
  `.ps_assert_number()`, `.ps_assert_writable_file()`). Messages name the
  argument in quotes (`'x' must be a DNAStringSet`) and use `call. = FALSE`.
  Add a check there rather than writing a new one in place.
- **Warnings and errors.** Warn when the analysis can go on and the user
  should know what was dropped (promoters of another length or rich in `N`,
  identifiers absent from a background); say how many. Stop when the result
  would be meaningless (promoters shorter than a motif, too few observations
  for the z-test), and say which input is at fault.
- **Comments** explain why, not what. No commented-out code.
- **Dependencies.** Packages needed only by some functions or by the
  vignettes (JASPAR releases, genome and annotation packages) are in
  `Suggests`, and code that needs one checks it with `requireNamespace()`
  first. PscanRBackgrounds is in `Suggests` too: the code reaches its files
  through ExperimentHub (in `Imports`) and never loads it.
- **AI assistance.** Source files written or changed with substantial AI
  assistance carry an `Assisted-by:` note (see `inst/PROVENANCE.md`).
- **NEWS and version.** Each user-visible change gets an entry in `NEWS.md`
  under the next version. `Version` in `DESCRIPTION` is increased (0.99.z
  during review, then the Bioconductor scheme) once per push to the
  Bioconductor repository, because the build system builds only new versions.

## Checking a change

- Tests: `devtools::test()` or `testthat::test_local()`.
- Documentation: `roxygen2::roxygenise()`, then check that the `man/`
  changes are the intended ones.
- Lint: `lintr::lint_package()`.
- Full check: `R CMD build`, `R CMD check` and `BiocCheck::BiocCheck()`
  on the tarball.
- Coverage: `covr::package_coverage(type = c("tests", "examples"))`; 85% of
  lines in November 2026.
- Refactors that should not change results: run the examples of all manual
  pages with the old and the new version and compare the objects they
  return.

Continuous integration (`.github/workflows/`) runs on pushes and pull
requests to `main` and `devel`, and can be started by hand:

- `check-bioc.yml`: job `check` runs R CMD check and BiocCheck on Ubuntu with
  Bioconductor devel; job `lint` runs lintr and fails on any lint.
- `r-universe.yml` ("Submission platforms"): the r-universe build on Linux,
  macOS and Windows.

## Branches and releases

- `main` is the version submitted to Bioconductor. Changes reach it only
  through pull requests, which the maintainer merges.
- Work is done on topic branches; AI-assisted work is on `Claude`. Bring a
  topic branch up to date with `main` before starting new work on it.
- During the review, `main` is pushed to the `devel` branch of
  <https://github.com/BiocStaging/PscanR>, and each push with a new version
  triggers a build report on the review issue.
- After acceptance, `main` is pushed to the `devel` branch of
  `git.bioconductor.org/packages/PscanR` (SSH keys registered in
  BiocCredentials). Fixes for a released version go to its `RELEASE_3_xx`
  branch as well. GitHub `main` and Bioconductor `devel` are kept identical.

## Adding a JASPAR release or new backgrounds

The background files are produced by
<https://github.com/Federico77z/PscanRBackgrounds-pipeline>, which writes the
files and a `catalog.tsv`.

1. Generate the backgrounds with the pipeline.
2. Deposit the files on Zenodo, one record per JASPAR release, and update the
   archive record if needed.
3. Add the rows to `inst/extdata/PscanR_background_catalog_v2.tsv`. They must
   agree with the pipeline's `catalog.tsv`, checksums included.
4. Add the release and its Zenodo record to `.ps_zenodo_file_records` in
   `Helper_functions.R`.
5. For a new JASPAR release, add its package to `Suggests` and a branch to
   `.ps_load_jaspar_collection()` in `Build_Background.R`.
6. In PscanRBackgrounds, add the records to `inst/extdata/metadata.csv`
   (with `inst/scripts/make-metadata.R`), increase the version and ask the
   Bioconductor Hub team to upload the files. The titles must match
   `.ps_hub_title()`.
7. Update the tests in `test-Background_backends.R` and
   `test-Background_catalog.R` that check the catalog contents.
